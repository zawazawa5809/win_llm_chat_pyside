# 社内エンドポイント追加仕様書・導入ガイド

## 目的

- 既存の **Ollama / OpenAI 互換エンドポイント** に加えて、社内でホストしている独自エンドポイントを GUI から選択・利用できるようにする。
- ログイン認証・セッション管理・チャット送信・添付送信を最小構成として、将来的な拡張（モデル一覧取得、利用制限、監査ログ連携など）にも対応できる設計指針を提供する。

## アプリの基本的な使い方（再確認）

1. アプリを起動し、右上の **「設定」→「接続設定...」** を開く。
2. 「プロバイダー」選択で **Ollama** または **OpenAI 互換** を選び、ベース URL・モデル名・API キー（必要に応じて）を入力。
3. 設定保存後、右ペイン上部の **「チャット」タブ** でメッセージを入力して送信。
4. 添付ファイルを付けたい場合は **「添付」タブ** に切り替え、ファイルを追加後にチャットへ反映して送信。
5. セッションは自動保存され、左ペインのセッション一覧から再開できる。

## 社内エンドポイント追加の設計方針

### 基本要求

- **通信プロトコル**: HTTPS 推奨（HTTP でも動作は可能だが社内 CA 証明書の配布を前提）。
- **API 互換性**: 既存実装は `BaseLlmClient`（`services/llm_client.py`）の `send_chat` / `iter_chat` を利用。社内エンドポイント向けクライアントもこの 2 メソッドを実装する。
- **ストリーミング**: SSE または JSON Lines を推奨。非対応の場合は `iter_chat` で単一応答を 1 回だけ `yield` すればよい。
- **エラー設計**: HTTP ステータスとアプリ内エラー（`NetworkError` / `AuthenticationError` / `ResponseFormatError`）を対応付ける。認証失効時は `AuthenticationError` を返す。

### API インターフェース（例）

| 機能 | メソッド/パス | 入力 | 出力 | 備考 |
| --- | --- | --- | --- | --- |
| ログイン | `POST /v1/auth/login` | `{ "username", "password" }` | `{ "access_token", "refresh_token", "expires_in" }` | 2 種類のトークン発行を推奨 |
| トークン更新 | `POST /v1/auth/refresh` | `{ "refresh_token" }` | `{ "access_token", "expires_in" }` | 失効時は 401 を返す |
| モデル一覧 | `GET /v1/models` | ヘッダー `Authorization: Bearer <token>` | `{ "data": [{"id": "gpt-4o-mini"}, ...] }` | 任意だが UI からモデル候補を表示可能 |
| チャット（非ストリーム） | `POST /v1/chat/completions` | OpenAI 互換形式を推奨 | OpenAI 互換レスポンス | ストリーム非対応ならここを利用 |
| チャット（ストリーム） | `POST /v1/chat/completions` + `stream=true` | OpenAI 互換形式 | SSE `data: {"choices":[{"delta":{"content":"..."}}]}` | JSON Lines 形式でも可 |
| 添付アップロード | `POST /v1/files` | `multipart/form-data`（`file` フィールド） | `{ "file_id" }` | 返却 ID をチャットの `messages` 内 `content` に含めて送信 |
| セッション取得 | `GET /v1/sessions/{id}` | 認証ヘッダー | `{ "messages": [...] }` | 任意。サーバ側セッションと UI セッションの同期用 |

### データモデル・状態管理

- **認証情報**: `access_token` と `refresh_token` をアプリ設定に保存（暗号化は OS 依存、最低でもローカルファイル権限で保護）。
- **セッション**: アプリ内セッション ID とサーバ側セッション ID をマッピングするフィールドを持たせる（例: `server_session_id`）。
- **添付**: `file_id` と MIME を保持し、プロンプトに埋め込む形で送信。テキスト抽出が必要な場合はサーバ側で行い、`content` に変換後返却。

## 実装ガイド（開発者向け）

1. **クライアント実装の追加**
   - `src/win_llm_chat_pyside/services/llm_client.py` に `InternalApiClient`（仮称）クラスを追加し、`BaseLlmClient` プロトコルの 2 メソッドを実装。
   - 認証ヘッダー付与やリフレッシュ処理をこのクラス内で完結させる。401 を受け取ったら自動リフレッシュしてリトライする設計が望ましい。

2. **設定項目の拡張**
   - `core/config.py` にプロバイダー種別（例: `provider: "internal"`）と認証情報格納用キー（`username`/`password` または `refresh_token` 等）を追加。
   - 設定ダイアログ（`features/chat` または `ui/dialogs` 配下の接続設定 UI）に社内プロバイダーを選択する選択肢と入力欄を追加。

3. **プロバイダー切り替えロジック**
   - `core/factory.py` または該当する組み立て箇所でプロバイダー種別を参照し、`OpenAiCompatibleClient` / `Ollama` / `InternalApiClient` を生成する分岐を追加。

4. **セッション管理連携**
   - `features/sessions` 内で、サーバ側セッション ID を保持するフィールドを追加し、チャット送信時にヘッダーやペイロードに含めるよう調整。
   - サーバ側履歴を再取得する場合はセッション読み込み時に `GET /v1/sessions/{id}` を呼び、UI のメッセージリストに反映。

5. **添付送信フロー**
   - `features/attachments` でアップロード先を社内 API に切り替える場合、まず `POST /v1/files` で `file_id` を取得し、`messages` の `content` にメタデータを付与する形でチャット送信に渡す。
   - 既存のローカル変換パス（テキスト抽出など）があれば維持しつつ、アップロード併用を許可する。

6. **ログ/エラーの扱い**
   - 共通のロギングポリシー（`docs/LOGGING_POLICY.md`）に従い、トークンや個人情報はログ出力しない。
   - エラーはユーザーに分かりやすいメッセージ（認証失効・ネットワーク断・レスポンス異常）で通知。

## 導入（運用）手順

1. **社内 API 側の準備**
   - 上記 API パスをデプロイし、SSE or JSON Lines のストリーミング応答を確認。
   - テスト用アカウントとサンプルモデルを用意し、CORS/ネットワーク到達性を確認。

2. **アプリ設定**
   - 新バージョンに更新後、「接続設定」でプロバイダーに **Internal**（仮称）を選択。
   - ベース URL、モデル名、ユーザー名/パスワード（または API キー）、必要なら CA 証明書パスを入力して保存。

3. **初回ログイン**
   - 保存時に `POST /v1/auth/login` を実行し、取得した `access_token` / `refresh_token` をローカル保存。
   - 失敗した場合は資格情報を再入力。多要素認証がある場合は追加画面や CLI 連携を検討。

4. **チャット利用**
   - 通常のチャットと同様にメッセージを送信。`stream=true` が有効ならストリーミング表示される。
   - 添付タブからファイルをアップロードすると、`file_id` を含むメッセージとして送信され、サーバ側で前処理後に回答が返る。

5. **トークン更新**
   - アクセストークン失効時は自動リフレッシュを行う。連続失敗した場合はログアウト状態とし、再ログインを促す。

6. **トラブルシューティング**
   - **認証系**: 401/403 が続く場合はトークン失効・権限不足を確認。ログにはトークン本体を出力しない。
   - **ネットワーク**: プロキシ設定や証明書エラーを確認。必要に応じてベース URL を HTTP に変更して切り分け。
   - **レスポンス形式**: OpenAI 互換形式を満たしているかを確認。ストリームの場合は `data:` 行を 1 行 1 JSON で返す。

## 推奨テストシナリオ

- ログイン成功・失敗のハンドリングとリトライ。
- トークン失効→リフレッシュ→再送信のフロー。
- ストリーミング応答が途切れた場合の復旧（UI が停止せずエラーメッセージを表示）。
- 添付アップロード後のチャット送信（大容量ファイルを含む）。
- サーバ側セッション復元 → UI セッションへの適用。
- モデル一覧取得（任意）→ UI へのモデル選択肢反映。
