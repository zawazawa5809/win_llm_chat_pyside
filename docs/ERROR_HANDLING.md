# エラーハンドリング方針（v1.8）

アプリケーション全体でのエラー分類・処理・ユーザー通知のルールを定義する。

## エラー分類

### 1. ネットワークエラー
- **原因:** 接続失敗、タイムアウト、HTTP エラー
- **例外型:** `NetworkError`（`client.py` で定義）
- **ユーザーメッセージ:** 
  - タイムアウト: "応答がタイムアウトしました"
  - 接続失敗: "サーバーへの接続に失敗しました"
  - HTTP 401/403: "認証に失敗しました（API キーを確認してください）"
  - HTTP 404: "エンドポイントが見つかりません"
  - HTTP 429: "リクエストが多すぎます（しばらく待ってから再試行）"
  - HTTP 5xx: "サーバでエラーが発生しました"
  - その他: "通信でエラーが発生しました"
- **ログ:** `app_logger.error("client.network_error", {...})`
- **処理:** UI 上でエラーメッセージを表示し、ユーザーに再試行を促す

### 2. 認証エラー
- **原因:** API キーが無効、認証トークンが期限切れ
- **例外型:** `AuthenticationError`（`client.py` で定義）
- **ユーザーメッセージ:** "認証に失敗しました（API キーを確認してください）"
- **ログ:** `app_logger.error("client.auth_error", {...})`（API キーはフィルタリング）
- **処理:** 設定画面への誘導を促す

### 3. レスポンス形式エラー
- **原因:** LLM からの応答が期待される形式と異なる
- **例外型:** `ResponseFormatError`（`client.py` で定義）
- **ユーザーメッセージ:** "不正な応答を受信しました"
- **ログ:** `app_logger.error("client.response_format_error", {...})`
- **処理:** エラーメッセージを表示し、再試行を促す

### 4. ファイル I/O エラー
- **原因:** ファイル読み込み失敗、書き込み失敗、権限エラー
- **例外型:** `FileNotFoundError`, `PermissionError`, `OSError` など
- **ユーザーメッセージ:** 
  - ファイルが見つからない: "ファイルが見つかりません: {パス}"
  - 権限エラー: "ファイルへのアクセス権限がありません: {パス}"
  - その他: "ファイル操作でエラーが発生しました: {エラー内容}"
- **ログ:** `app_logger.error("storage.io_error", {"path": "...", "error": "..."})`
- **処理:** エラーメッセージを表示し、代替操作を促す

### 5. JSON パースエラー
- **原因:** 設定ファイルやセッションファイルの JSON が破損
- **例外型:** `json.JSONDecodeError`
- **ユーザーメッセージ:** "設定ファイルの読み込みに失敗しました。バックアップファイルがあれば復元を試みてください。"
- **ログ:** `app_logger.error("storage.json_parse_error", {"path": "...", "error": "..."})`
- **処理:** デフォルト値で続行するか、バックアップからの復元を試みる

### 6. 未処理例外
- **原因:** 予期しない例外（バグ）
- **例外型:** 任意の `Exception`
- **ユーザーメッセージ:** "アプリケーションで予期しないエラーが発生しました: {エラー内容}\n\n詳細はコンソールログを確認してください。"
- **ログ:** `app_logger.error("app.unhandled_exception", {"exc_type": "...", "exc_value": "..."})`
- **処理:** `app.py` の `exception_hook` でキャッチし、ユーザーに通知

## エラーハンドリングの原則

### 1. 例外は発生源に近い場所でキャッチ
- ネットワークエラー: `client.py` でキャッチし、`NetworkError` に変換
- ファイル I/O エラー: リポジトリ層でキャッチし、ログに記録してから再スローまたはデフォルト値で続行

### 2. ユーザー向けメッセージは明確に
- 技術的な詳細（スタックトレース、内部エラーコード）はユーザーに表示しない
- ユーザーが取るべき行動（設定確認、再試行など）を明示する

### 3. ログには十分なコンテキストを記録
- エラー発生箇所、操作内容、関連する ID（セッション ID、ファイルパスなど）
- センシティブ情報（API キー、プロンプト本文）はフィルタリング

### 4. UI を巻き込んでクラッシュさせない
- ワーカースレッドでの例外は `failed` シグナルで UI スレッドに伝達
- UI スレッドでの例外は `try/except` でキャッチし、エラーダイアログを表示

## エラーメッセージの統一

### メッセージ形式
```
[操作名]でエラーが発生しました: [具体的なエラー内容]

[ユーザーが取るべき行動]
```

### 例
```
メッセージ送信でエラーが発生しました: 応答がタイムアウトしました

ネットワーク接続を確認してから、もう一度お試しください。
```

## リトライポリシー

- **リトライしない:** 認証エラー、レスポンス形式エラー、ファイル I/O エラー
- **リトライを検討:** ネットワークエラー（タイムアウト、一時的な接続失敗）
  - 現時点では自動リトライは実装していない（ユーザーに手動再試行を促す）
  - 将来的に実装する場合は、指数バックオフ + 最大試行回数の制限を設ける

## エラーログの出力例

```python
# ネットワークエラー
app_logger.error("client.network_error", {
    "base_url": "http://localhost:11434",
    "model": "gemma3:4b",
    "error_type": "timeout",
    "timeout_seconds": 30
})

# ファイル I/O エラー
app_logger.error("storage.io_error", {
    "path": "/path/to/session.json",
    "operation": "read",
    "error": "Permission denied"
})

# 未処理例外
app_logger.error("app.unhandled_exception", {
    "exc_type": "ValueError",
    "exc_value": "Invalid session ID"
})
```
