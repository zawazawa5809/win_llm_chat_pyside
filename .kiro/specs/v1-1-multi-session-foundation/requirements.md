# Requirements Document

## Project Description (Input)

@ROADMAP-v2.0.md の v1.1:マルチセッション基盤

## Requirements

### Scope

- インスコープ: 複数セッション（会話スレッド）を管理するための Session モデル、セッション一覧 UI、セッション永続化とロードの仕組み、単一セッションからマルチセッションへの移行に必要な最小限の振る舞い
- アウトオブスコープ（本仕様）: 複数ユーザーやサーバー側共有セッション、チームコラボレーション機能、全文検索・ベクタ検索、RAG、セッションの自動アーカイブ/バックアップ、クラウド同期

### Functional Requirements

- FR-1 セッションモデル
  - アプリケーション内部で `Session` を表現するモデルを定義し、少なくとも `id`, `name`, `created_at`, `updated_at`, `messages[]` を保持できること
  - `id` はローカル環境内で一意となる識別子であること（例: UUID など）
  - `messages[]` は既存の単一セッションで利用しているメッセージ構造と互換性を保つこと
- FR-2 セッション一覧 UI
  - メインウィンドウ内にセッション一覧を表示する領域（左ペインまたはドロワーなど）を提供すること
  - ユーザーが以下の操作を行えること
    - 新規セッション作成
    - セッション名の変更
    - セッションの削除（確認ダイアログなどで誤操作を防止）
    - セッションの選択（アクティブセッション切り替え）
  - アクティブなセッションが一覧上で視覚的に分かること
- FR-3 セッション永続化
  - セッションデータの永続化方式を JSON または SQLite のいずれか 1 つに統一して利用すること
  - 各セッションについて、少なくとも `id`, `name`, `created_at`, `updated_at`, `messages[]` が永続化されること
  - アプリ終了時または適切なタイミングでアクティブセッションの変更内容が失われないよう保存されること
- FR-4 起動時のロード戦略
  - アプリ起動時にセッション一覧のメタデータ（`id`, `name`, `created_at`, `updated_at` 程度）をロードし、一覧 UI に表示すること
  - 起動時にはセッションの全文メッセージはロードせず、ユーザーがセッションを選択したタイミングで当該セッションの `messages[]` をロードすること
- FR-5 セッション切り替え
  - ユーザーがセッション一覧から別のセッションを選択した際、そのセッションのメッセージ履歴がチャット画面に表示されること
  - 切り替え前のセッションに未保存の変更がある場合、適切なタイミングで保存またはユーザーに通知されること
- FR-6 既存単一セッションからの移行
  - v1.0 までに存在する単一セッションの履歴がある場合、それを何らかの形でマルチセッション構造に取り込めること（例: 初期セッションとして 1 件作成）
  - 移行によって既存ユーザーの履歴が失われないこと

### Non-Functional Requirements

- NFR-1 メモリ使用
  - セッション数が増えても「一覧はメタデータのみ・開いているセッションだけ全文ロード」という方針により、常駐メモリ使用量が v1.0 と比較して極端に増加しないこと
  - セッション数が数十〜数百程度であっても、通常利用に支障がないメモリ使用量であること
- NFR-2 性能
  - 起動時に全セッションの全文メッセージをロードしないことで、起動時間が実用的な範囲に収まること
  - セッション切り替え時のロード処理により UI が著しくフリーズしないこと（数千メッセージレベルを想定）
- NFR-3 UX / 操作性
  - セッションの作成・名前変更・削除・切り替えが、LLM クライアント利用中の自然なフローの中で行えること
  - セッション名はユーザーが「案件名／プロジェクト名」などを付けてワークスペースとして使える程度の長さと表示幅を持つこと
- NFR-4 拡張性
  - 将来の機能（テンプレート・役割プロファイル、ファイル添付、検索など）がセッション単位で紐づけられるよう、Session モデルや永続化形式が拡張しやすい構造になっていること

### Acceptance Criteria

- AC-1 複数のセッションを作成し、それぞれに別々のメッセージ履歴を持たせた上で切り替えられること
- AC-2 アプリ再起動後も、作成したセッション一覧と各セッションのメッセージ履歴が保持されていること
- AC-3 セッション数が数十件になっても、起動時間と通常操作時のメモリ使用量が実用的な範囲に収まっていること
- AC-4 既存単一セッションの履歴を持つユーザーがアップデートした際に、少なくとも 1 つのセッションとして履歴が参照可能であること
- AC-5 セッション名を使って「案件／プロジェクト」単位で会話を整理し、業務利用に耐えるレベルでセッション管理が行えること
