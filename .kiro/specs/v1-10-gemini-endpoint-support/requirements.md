# Requirements Document

## Project Description (Input)

gemini のエンドポイントに対応したい

## Requirements

### Scope

- インスコープ: Windows デスクトップ版 LLM チャットクライアントにおいて、Google Gemini 系モデルをバックエンドとして利用できるようにするためのエンドポイント対応（プロファイル設定、認証、リクエスト送信、レスポンス表示、基本的なストリーミング対応）。対象は OpenAI 互換 `/v1/chat/completions` サーフェスを提供する Gemini API またはそれと互換なプロキシ / ゲートウェイとする。
- インスコープ（既存機能との整合性）: v1.4「軽量ファイル添付」および v1.8「クリップボード画像貼り付け」で定義された「添付ファイルはクライアント側でテキスト抽出し、生バイナリはバックエンドに送らない」という前提を、Gemini プロファイル利用時にも維持すること。
- アウトオブスコープ: Gemini ネイティブ `generateContent` API など OpenAI 互換ではないエンドポイント、画像・音声などマルチモーダル入力、ツール呼び出し / Function Calling、Gemini 固有のセーフティ設定 UI、課金・レート制限の管理機能。

### Functional Requirements

- FR-1 Gemini 用接続プロファイル

  - ユーザーは既存の「接続先プロファイル」機能を用いて、Gemini 向けのプロファイルを新規作成できなければならない。
  - Gemini プロファイルでは、少なくとも「表示名」「API ベース URL」「モデル名」「API キー」を設定できなければならない。
  - Gemini プロファイルは OpenAI / Ollama プロファイルと並列に扱われ、プロファイル一覧から選択・切り替えできなければならない。

- FR-2 OpenAI 互換チャット API へのリクエスト送信

  - Gemini プロファイルが選択されている場合、チャット送信時に OpenAI 互換 `/v1/chat/completions` エンドポイントへ `model`・`messages`・`stream` などの基本パラメータを含む JSON を送信しなければならない。
  - 送信するメッセージリストは、既存の Message モデル（role: system/user/assistant）から Gemini の OpenAI 互換サーフェスと整合する形で変換されなければならない。
  - プロファイルが Gemini であること以外に、ユーザーはチャット送信 UI の操作フローを意識的に切り替える必要があってはならない。

- FR-3 非ストリーミング応答のハンドリング

  - `stream: false` またはストリーミング未使用のリクエストでは、HTTP 200 応答時に `choices[0].message.content` 相当のテキストを抽出し、既存のチャットメッセージと同様にタイムラインへ表示しなければならない。
  - レスポンス形式が期待と異なる場合は、アプリがクラッシュせず、ユーザーに簡潔なエラーメッセージを提示しつつログに詳細を残さなければならない。

- FR-4 ストリーミング応答（可能な範囲）のハンドリング

  - Gemini の OpenAI 互換エンドポイントが SSE ベースのストリーミング応答を提供する場合、既存のストリーミング表示機構（増分テキスト描画、停止ボタンなど）を用いてチャット内容が逐次更新されなければならない。
  - ストリーム中に一部フレームが欠損・破損した場合でも、全体のストリームが即座に中断されるのではなく、可能な範囲で残りのフレーム処理を継続しなければならない。
  - ストリーミングが利用できない環境では、自動的に非ストリーミングモードへフォールバックし、ユーザー操作を追加で要求してはならない。

- FR-5 認証・エラー時の挙動

  - API キーが未設定または無効な場合、Gemini エンドポイントへのリクエストは行われず、ユーザーに「認証情報不足」であることが分かるエラーを表示しなければならない。
  - HTTP ステータス 401/403 の場合は認証エラーとして扱い、それ以外の 4xx/5xx はネットワークまたはサーバーエラーとして分類し、ログにはステータスコードと短いメッセージのみを記録しなければならない（API キー等の秘匿情報は含めない）。
  - ネットワークタイムアウトや接続失敗時も、アプリがハングまたはクラッシュせず、ユーザーに再試行可能であることが分かるメッセージを提示しなければならない。

- FR-6 既存エンドポイントとの共存

  - Gemini プロファイルの追加・切り替えにより、既存の OpenAI 互換 / Ollama プロファイルの挙動が退行してはならない。
  - 1 回のアプリ起動中にプロファイルを OpenAI ⇄ Gemini ⇄ Ollama と切り替えても、セッション履歴・UI 状態が破壊されず、チャット送信が継続できなければならない。

- FR-7 添付ファイル・画像添付フローの互換性

  - Gemini プロファイル選択時でも、v1.4 で定義されたファイル添付の要約・Q&A アクションは、OpenAI プロファイル利用時と同等の UX と制約で利用できなければならない。
  - 添付ファイルおよびクリップボード画像（v1.8）の生バイナリは、Gemini API に対して直接送信されてはならず、クライアント側で抽出・生成されたテキストのみが `messages` に含まれなければならない。
  - 画像添付やファイル添付を含むメッセージを Gemini プロファイルで送信した場合でも、セッションの添付一覧・画像サムネイル表示・再利用フローが OpenAI プロファイル利用時と同等に動作しなければならない。

### Non-Functional Requirements

- NFR-1 パフォーマンスと応答性

  - 一般的なネットワーク環境において、Gemini プロファイルでのチャット送信から最初のレスポンステキスト（またはストリーム開始）が表示されるまでの体感時間が、同条件の OpenAI 互換エンドポイント利用時と同程度の範囲に収まっていなければならない。
  - タイムアウトやリトライ処理は、ユーザーの操作感に過度な遅延や UI フリーズを発生させないように設計されなければならない。

- NFR-2 セキュリティと秘匿情報の取り扱い

  - Gemini 用 API キーは設定ファイルまたは環境変数などから読み込まれ、コードへのハードコーディングやログ出力が行われてはならない。
  - エラーログや診断情報には、API キーや個人情報を特定しうるリクエストボディの全文を含めてはならない。

- NFR-3 拡張性と保守性

  - Gemini 向けの実装は、既存の OpenAI / Ollama 実装と同様に API 種別ごとに責務が分離された構造を維持し、将来的に追加の LLM ベンダーをサポートできる拡張性を損なってはならない。
  - Gemini 固有オプション（例: セーフティ設定など）を将来追加できるよう、リクエストオプションの拡張ポイントを意図的に残しておかなければならない。

### Acceptance Criteria

- AC-1 有効な Gemini API キーとベース URL・モデル名を設定したプロファイルでチャットを送信した場合、エラーなく Gemini 由来の応答がチャットタイムラインに表示されることを確認できること。
- AC-2 意図的に無効な API キーや権限のないプロジェクトを設定した場合、ユーザー向けには認証エラーが明示され、ログ上ではステータスコードと簡潔なメッセージのみが記録され、API キー等が含まれていないことを確認できること。
- AC-3 同一アプリ起動中に OpenAI プロファイルでの送信 → Gemini プロファイルでの送信 → Ollama プロファイルでの送信を連続して実行しても、セッションが壊れず、各バックエンドから適切な応答が得られること。
- AC-4 追加された自動テストおよび既存のテストスイートを実行した際に、Gemini 対応の追加によって既存機能に回帰バグが発生していないことが確認できること。
- AC-5 ファイル添付（v1.4）およびクリップボード画像添付（v1.8）を利用した要約・Q&A・通常チャットの代表的なシナリオを、OpenAI プロファイルと Gemini プロファイルの両方で実行した際に、いずれも添付リスト・画像表示・セッション履歴が破壊されず、Gemini 側のリクエストに添付バイナリが含まれていないことをログ等で確認できること。
